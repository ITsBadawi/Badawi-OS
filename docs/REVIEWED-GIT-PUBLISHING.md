# Reviewed Commit and Push

The Projects modal now lists changed paths with recently modified files first. The owner selects exact paths, enters a message and author identity, then reviews the repository, branch, old HEAD and selected paths. A separate five-minute, one-use approval creates a local Commit. It never pushes as part of that approval. The actual Git index must be clean before preview. Existing staged content, secret-like paths, symlinks, hard links, submodules, files above 10 MiB and batches above 40 MiB are refused. The preview fingerprints the full change list and selected file bytes, and a changed project/root/HEAD/branch/file invalidates approval. Git hooks, signing, filters and credential helpers are disabled or unsafe repository configuration is refused. A failed operation can leave the selected files staged; inspect Git status before retrying. No working file is reset or deleted.

Push has a separate preview and approval. It requires a linked GitHub owner/repo/branch and a protected GitHub token with Contents write permission. The remote branch HEAD is read through GitHub's official API, checked as an ancestor of local HEAD, and re-read before transfer. Git pushes only `HEAD` to that exact GitHub HTTPS branch, with no tags or hooks; GitHub's response is checked again before recording a confirmed receipt. A failed or interrupted push may have reached the server: the app reports an unconfirmed result unless an independent remote read proves the exact commit arrived. A failed confirming read also remains unconfirmed. The owner should inspect GitHub before retrying; the local Commit is preserved. A private synthetic owner repository was used for live Push acceptance, with no real project files.

The owner can ask Badawi in a project conversation which files to include or exclude. With selected-project or independently granted AI read scope, `git.changes` supplies at most 100 eligible changed filenames/times to the assistant; blocked secret-like names are withheld, and a selected single-file conversation cannot read this repository-wide list. The assistant may return `git.selection.propose` with the exact observed HEAD/status fingerprint, paths and explanation. This creates the normal owner approval card. Approval preselects those checkboxes in the Projects picker; the owner may change any checkbox and must still review the Commit and Push separately. Changed repository state invalidates the transient suggestion. The assistant cannot stage, commit or push, and a recommendation never authorizes sending file contents or writing code.

Current limits: simple initialized repositories with a local branch; no staged changes, Git worktrees, custom attributes/filters, non-GitHub remotes, diverged branches or multi-branch publishing. These remain parity work. A controlled native test covered UI selection, secret-path blocking, exact local Commit and separate Push preview. A subsequent isolated live test used a private synthetic repository under `itsbadawiit`, authenticated clone, exact local Commit and actual Push; GitHub returned the same immutable commit and an independent connected GitHub read found the synthetic file. A second live private repository started empty: the app cloned it with no remote HEAD, made its first reviewed Commit, pushed the new branch and confirmed the SHA. Five additional native checks used controlled GitHub responses to verify in-flight Clone cleanup, interrupted Push uncertainty, lost response with unchanged or exact-match remote HEAD, and missing confirmation after a successful Git response. These checks did not interrupt a live GitHub transfer. Test credentials were removed from the temporary app profiles, which were deleted.
