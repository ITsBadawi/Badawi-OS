# Arabic and English

The owner can change **Settings → App language** between العربية and English. The preference is local and persists across restarts. Existing profiles default to Arabic. This is available in the current source build; the earlier packaged 0.3.0 release has not been replaced.

Navigation, labels, dialogs, tool policies, validation messages and operational feedback use a local dictionary. Document direction, alignment, the assistant launcher, mobile navigation, dates, calendar headings and number formatting follow the selected language. Technical paths, model IDs and source code retain their own direction. English assets load on demand from the compiled local application; changing language makes no provider request and grants no permission.

Owner content is never machine-translated. Saved note bodies, task titles, conversations, file names, project descriptions and historical receipts retain their exact original text. Newly generated local reminders, automation alerts, project inspection summaries and native dialogs use the owning profile's language. The default scheduled AI briefing prompt asks for that language; this still needs the existing independent source consent, provider configuration and budget authorization. A model's answer to an owner-written prompt is not forcibly translated.

Implementation:

- `src/localization.ts` provides exact local translation, parameter formatting and reactive static label maps. Dynamic owner values are inserted after translation and are never used as dictionary keys.
- `src/core/host-localization.ts` resolves language from the owning Store on every call. Renderer state cannot select another profile's notification language.
- `src/locales/english.data.json` is the maintained English dictionary; `english.ts` is generated by `scripts/set-english.mjs`. The numeric batch files are authoring inputs, not runtime dependencies.
- `scripts/localization-inventory.mjs` reads source syntax using the installed Prettier TypeScript parser. It currently finds 1,471 distinct Arabic source strings/templates across renderer, core and desktop code, all covered by English entries. Some occur in multiple areas. The bilingual language-picker label and native language names intentionally stay recognizable in both languages.
- Missing English keys fall back to their Arabic source instead of producing empty controls. The coverage test rejects a missing current inventory key or changed interpolation parameters.

Verification includes the full core suite, inventory coverage, real Store restart, profile-specific host reminders, exact owner-data preservation, native English page traversal and task views/editor, English-to-Arabic switching and restart. Native checks use an isolated synthetic profile and forbid external requests. They do not establish real provider eligibility or prove every linked-account flow. See `validation/localization-desktop.json` for the current native result. The broader feature-parity and release acceptance remain open.
